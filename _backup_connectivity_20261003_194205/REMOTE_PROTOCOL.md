# SWARM Remote Protocol v1 (PC bridge <-> Android companion)

Status: v1 (revision 2: peer-to-peer only, device-key mutual auth, WebSocket). The PC side (Electron main process, `electron/remote/`) implements this; the phone is the client. **There is no relay/cloud server.**

## 1. Transport
- HTTPS (TLS 1.2+) with a **self-signed certificate** generated once by the PC and kept in app userData.
- Default port **47821** (configurable on the PC). The bridge only listens while the user has it enabled.
- The phone MUST NOT trust the system CA store for this host. It **pins the SHA-256 fingerprint of the server certificate** (DER bytes of the leaf cert) obtained from the QR code. Hostname verification is skipped (hosts are bare IPs); the fingerprint match authenticates the PC. (OkHttp: custom X509TrustManager comparing `sha256(chain[0].encoded)` + `hostnameVerifier { _, _ -> true }`.)
- All HTTP bodies are `application/json; charset=utf-8`. Max request body 64 KB.
- The PC offers the same HTTPS port for REST and for the WebSocket upgrade (`wss://host:port/v1/ws`).

## 2. QR payload
The QR encodes compact JSON (UTF-8):

```json
{"v":1,"hosts":["192.168.1.20:47821","[2401:db8::5]:47821","203.0.113.7:47821"],"fp":"<64 hex chars, lowercase>","tok":"<base64url pairing token>","name":"Harman-i5"}
```
- `v`: protocol version (1).
- `hosts`: candidate `host:port` endpoints **in priority order**: (1) LAN IPv4 addresses, (2) global public IPv6 addresses (IPv6 literals are bracketed: `[addr]:port`), (3) UPnP/NAT-PMP-mapped public `host:port`, (4) optional user-configured public `host:port` (manual port-forward / DDNS name). There is no relay. Phone tries them in order with a short connect timeout (~2-3 s each; a "happy eyeballs" race is fine) and picks the first whose `GET /v1/ping` succeeds with a certificate matching `fp`. It should store the whole list and retry/re-rank on every reconnect (networks change: home Wi-Fi vs mobile data).
- `fp`: SHA-256 of the DER-encoded server certificate, lowercase hex, no colons.
- `tok`: one-time pairing token (32 random bytes, base64url, no padding). **TTL 120 seconds, single use**, invalidated after 5 failed attempts.
- `name`: human-readable PC name.

## 3. Device key (mutual authentication)
The phone generates a **per-pairing ECDSA P-256 key pair** (Android Keystore, non-exportable, `SHA256withECDSA`). The PC stores the public key at pairing and afterwards every request must be signed by that key *in addition to* carrying the device secret. Unknown keys / bad signatures are rejected.

- Public key encoding on the wire: **base64 (standard, padded) of the X.509 SubjectPublicKeyInfo DER** = Android `publicKey.encoded`.
- Signature encoding: **base64url (no padding) of the ASN.1 DER ECDSA signature** = the output of Android `Signature.getInstance("SHA256withECDSA")`.

## 4. Pairing
`POST /v1/pair` (no Authorization header)
```json
{"token":"<tok>","deviceName":"Pixel 8","deviceId":"<random uuid v4 generated by phone>","publicKey":"<base64 SPKI DER>","proof":"<signature>"}
```
`proof` = signature (by the device private key) over the UTF-8 string
`"SWARM-PAIR-1\n" + token + "\n" + deviceId + "\n" + publicKey`
(proves possession of the private key).

Success `200`:
```json
{"deviceId":"<same uuid>","deviceSecret":"<base64url, 32 random bytes>","pcName":"Harman-i5","v":1}
```
- The secret is shown ONCE. The phone stores it (encrypted storage) with the pinned `fp` and the host list. The PC stores only a salted SHA-256 hash of it plus the public key.
- Errors: `400 {"error":"bad_request"}`, `401 {"error":"invalid_token"}` (unknown/expired/used token or bad proof; same response), `409 {"error":"device_exists"}`, `429 {"error":"rate_limited"}` (+ `Retry-After`).
- To re-pair, generate a new deviceId + key pair.

## 5. Authentication for all other endpoints
Every request (REST and the WebSocket upgrade) carries:

| Header | Value |
|---|---|
| `Authorization` | `Bearer <deviceId>.<deviceSecret>` (UUID contains no `.`; split on the first `.`) |
| `X-Swarm-Timestamp` | current Unix time in **milliseconds** (decimal string). PC accepts \|skew\| <= 60 s |
| `X-Swarm-Nonce` | random >= 16 bytes, base64url. Never reused within 5 minutes (replay protection) |
| `X-Swarm-Signature` | signature over the canonical string below |

Canonical string (UTF-8, `\n` separators, no trailing newline):
```
SWARM-REQ-1
<HTTP METHOD UPPERCASE>
<request target: path + query exactly as sent, e.g. /v1/agents/abc/start>
<timestamp>
<nonce>
<deviceId>
<lowercase hex SHA-256 of the raw request body bytes (empty body -> e3b0c442...b855)>
```
- Failure -> `401 {"error":"unauthorized"}` (+ `WWW-Authenticate: Bearer`). The response never says which factor failed.
- Repeated failures from one IP -> `429 {"error":"rate_limited"}` with `Retry-After`.
- Revoking a device on the PC makes its credentials fail immediately and closes its WebSockets (close code **4401**). Phone should treat 401 / close 4401 as "unpaired" and return to the scan screen.

## 6. REST endpoints
All responses JSON. Errors: `{"error":"<code>","message":"<optional>"}`.

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/v1/ping` | no | `{"ok":true,"v":1}` host probing / cert-pin check |
| POST | `/v1/pair` | token | see above |
| GET | `/v1/status` | yes | PC/bridge summary |
| GET | `/v1/agents` | yes | list of agents |
| POST | `/v1/agents/{id}/start` | yes | start/resume the agent |
| POST | `/v1/agents/{id}/stop` | yes | stop the agent |
| POST | `/v1/agents/{id}/task` | yes | body `{"text":"..."}` (1..8000 chars) |
| GET (upgrade) | `/v1/ws` | yes | WebSocket, see section 7 |

`GET /v1/devices` is NOT exposed remotely (device management is local-only in the PC UI).

**What an "agent" is on the PC:** SWARM's unit of work the user can start/stop/instruct is a *project* with its agent team/run. `id` = project id, `name` = project name. `start` begins a run of the project's objective (or resumes a paused run); `stop` cancels the active run; `task` sends the text as guidance to the running run's manager, or, if nothing is running, starts a new run with `text` as the objective.

### GET /v1/status -> 200
```json
{"v":1,"pcName":"Harman-i5","appVersion":"1.0.0","time":"2026-10-03T14:00:00.000Z","agentCount":3,"runningCount":1}
```

### GET /v1/agents -> 200
```json
{"agents":[
  {"id":"<string>","name":"My project","status":"running","task":"Short summary of current task or null","updatedAt":"2026-10-03T14:00:00.000Z"}
]}
```
- `status`: `idle` | `running` | `stopped` | `error` | `waiting` (paused / needs attention on the PC).
- `task`: short (<=200 chars) summary or `null`.
- Ids are opaque; URL-encode them in paths.

### POST .../start, .../stop, .../task -> 200
```json
{"ok":true,"agent":{ ...same shape as list item... }}
```
Errors: `404 {"error":"agent_not_found"}`, `400 {"error":"bad_request"}`, `409 {"error":"invalid_state"}`, `500 {"error":"internal"}`.

## 7. WebSocket `wss://host:port/v1/ws`
Authenticated by the same headers as section 5 on the upgrade request (signature over `GET` + `/v1/ws`, empty body). Android OkHttp: `Request.Builder().header(...)`. Frames are JSON text.

Server -> client:
- `{"type":"hello","v":1,"pcName":"...","time":"<iso>"}` right after upgrade.
- `{"type":"agents","agents":[...]}` pushed on connect and whenever any agent's status/task changes (coalesced, <= 1/s).
- `{"type":"result","id":"<client id>","ok":true,"data":{...}}` or `{"type":"result","id":"...","ok":false,"error":"<code>"}` replying to commands.
- `{"type":"pong","t":<echo>}`.

Client -> server (include a client-chosen string `id` to correlate):
- `{"type":"agents.list","id":"1"}` -> result `data: {"agents":[...]}`
- `{"type":"agent.start","id":"2","agentId":"..."}`; `agent.stop` same shape; `{"type":"agent.task","id":"3","agentId":"...","text":"..."}` -> result `data: {"agent":{...}}`
- `{"type":"status","id":"4"}` -> result `data` = `/v1/status` body
- `{"type":"ping","t":123}`
The server sends a WebSocket ping every 20 s and drops connections that do not answer. Reconnect with a fresh timestamp/nonce/signature.

Polling `GET /v1/agents` every 2-3 s always works as a fallback; WebSocket is preferred.

## 8. Reaching the PC from anywhere (no server)
v1 is **direct peer-to-peer**; nothing is relayed. The phone must be able to reach one of the `hosts`:
1. **LAN IPv4**: same Wi-Fi/LAN (or a VPN you run yourself such as WireGuard/Tailscale; their addresses show up as LAN IPs).
2. **Global IPv6**: if the PC has a public IPv6 address and the router/firewall allows inbound TCP to the port (Windows Firewall rule is added by the user/installer prompt), the phone can connect from mobile data directly.
3. **UPnP / NAT-PMP**: the PC asks the router to forward the external port to itself; works only if the router supports it, it is enabled, and the router has a real public IPv4 (not CGNAT / double NAT).
4. **Manual**: user enters a public `host:port` (DDNS name or IP) and sets up a router port-forward themselves.
If none of these works (CGNAT, IPv4-only ISP with UPnP off, strict firewall), the phone can only connect on the same network. The PC UI shows the status of every route honestly. Routes are pluggable on the PC (`RouteProvider` interface in `electron/remote/routes.ts`); the QR `hosts` list is just the union of the providers' addresses.

## 9. Security summary
- TLS with pinned self-signed cert (confidentiality + PC authentication).
- Pairing token: 32 random bytes, 120 s TTL, single use, 5 failed attempts max; proof-of-possession of the device key at pairing.
- Per-request: device secret (PC stores salted SHA-256 only, constant-time compare) AND ECDSA P-256 signature from the registered device key, timestamp window + nonce replay cache.
- Per-IP failure rate limiting; revocation immediate (also closes sockets); bridge off by default.
- The bridge never exposes file contents, secrets/API keys, or the device list.
